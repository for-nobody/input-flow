# ADR-000：仓库结构与技术选型

- 状态：已接受（Accepted）
- 日期：2026-09-26
- 涉及模块：全项目

## 背景（Context）

InputFlow 是 Windows 全局键盘与鼠标输入组合引擎：观察键鼠事件，暂扣可能构成已启用规则的事件，命中后消费并发送动作，失败/超时则按序回放。M0 需要固定仓库结构与技术选型，作为后续里程碑的基线。

## 候选方案（Options）

### 仓库结构
1. 一开始就建立 workspace（`crates/` + `apps/` + `tests/`）。
2. M1 先用单个 Cargo 包起步，待引擎与 Windows 接入需要独立测试时再演进为 workspace。

### Windows API 绑定
1. `windows` crate：高层安全封装，体积/编译成本较高。
2. `windows-sys` crate：原始 FFI 绑定，轻量、编译快，足够覆盖 LL Hook 与 `SendInput`。

### 输入接入与输出
- 接入：`WH_KEYBOARD_LL` / `WH_MOUSE_LL` 低级 Hook，专用消息循环线程。
- 输出：`SendInput`，检查返回值并处理 UIPI 限制。

## 取舍（Trade-offs）

- workspace 更清晰但会提前引入不必要的结构；单包起步迭代更快，M3 演进成本可控。
- `windows-sys` 更贴近“平台层集中管理 unsafe”的需求，编译更快；`windows` 的封装在需要时可再引入。

## 实验 / 依据（Evidence）

- 规划稿 7.1 明确“M1 可单包，待引擎与接入需独立测试时再演进为 workspace”。
- 规划稿第 7 节（技术选型表）与第 12 节官方资料给出 LL hook、`SendInput`、serde JSON、Tauri 2 的可行性边界。

## 最终决策（Decision）

- 语言/工具链：Rust stable（1.98.1，stable-x86_64-pc-windows-msvc）。
- Windows API：`windows-sys`（windows-rs 的原始绑定 crate）；M0/M1 用最小 API 验证，锁定版本写入 Cargo.lock 与 README。
- 输入接入：`WH_KEYBOARD_LL` + `WH_MOUSE_LL`，专用消息循环线程，回调内只做归一化与轻量决策。
- 输入输出：`SendInput`，带本程序 `dwExtraInfo` 标记并结合 injected 标志识别。
- 配置：serde + JSON，版本化、原子保存、坏文件回退（M6）。
- GUI：Tauri 2 + React + TypeScript（M7 才接入，前端不持有 Hook）。
- 仓库结构：M1 用单个 Cargo 包（`apps/probe-cli`），M3 起演进为 workspace（`crates/inputflow-engine`、`crates/inputflow-windows`）。

## 后果（Consequences）

- 现阶段只维护一个包，迭代快；M3 需要做一次到 workspace 的迁移（成本可控）。
- 所有 `unsafe`、Win32 资源清理与线程生命周期集中在 `platform/windows` 模块（后续），并说明不变量。
